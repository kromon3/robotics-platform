# Платформа подбора роботизированных решений

Веб-платформа экспресс-прединвестиционной оценки роботизации. Сквозной путь: параметры объекта → объяснимый подбор роботов из каталога → экономический расчёт по трём сценариям (без роботизации / покупка / RaaS) → 2D-имитация работы склада, подтверждающая расчёт → сохранение проекта и выгрузка отчёта.

Хакатон ФЦ БАС, кейс «Платформа подбора роботизированных решений».

## Запуск одной командой

Нужен только Docker.

```bash
docker compose up --build
```

Открыть **http://localhost:8080**

Поднимаются три контейнера: PostgreSQL, NestJS API и nginx со статикой фронтенда. При старте API накатывает миграции и засевает базу: роли, демо-аккаунты, каталог организатора (197 решений) и ТТХ роботов (48 решений с габаритами, грузоподъёмностью, скоростью и фотографиями).

Если порты 5432 / 3000 / 8080 заняты, скопируйте `.env.example` в `.env` и поменяйте `POSTGRES_PORT`, `API_PORT`, `WEB_PORT`.

### Демо-аккаунты

| Роль | Логин | Пароль |
|---|---|---|
| Администратор | `admin@robotics.local` | `admin12345` |

## Как посмотреть за 5 минут

1. **Роботы** — каталог из 197 решений: поиск, фильтры по типу, категории и статусу, сортировка, карточка с ТТХ, кейсами и источником данных.
2. **Проекты** → выбор типа объекта (склад / аэропорт / медучреждение; для двух последних открывается экран готовности направления) → **Склад** → «Заполнить примером» → «Подобрать роботов» — параметры демо-склада 40 × 24 м.
3. На витрине: **подходящие решения** с ТТХ и **исключённые с причиной** («нужен проход не уже 2,6 м, у вас 2 м»; «поднимает груз на 2,0 м, верхний ярус — 4,0 м»). Отметить «Сравнить» у двух-трёх решений — появится таблица сравнения с ТТХ, требуемым числом роботов и стоимостью парка. Выбрать Ronavi H1500 → «Выбрать для расчёта».
4. **Данные для экономики** → «Заполнить примером» → «Рассчитать». Грузопоток и габариты второй раз не спрашиваются — шаг «Хранение и операции» показывает введённое на первом экране.
5. **Экономический отчёт**: показатели с зонами (зелёная / жёлтая / красная), сравнение трёх сценариев, структура CAPEX и OPEX построчно с методом расчёта и источником, накопленный денежный поток, анализ чувствительности.
6. Вкладка **«Схема и имитация»**: план склада, роботы ездят, внизу — расчётная и фактическая производительность, загрузка, простои, вердикт «расчёт подтверждён».
7. **«Сохранить расчёт»** (после входа) → вкладка **«Расчёты»**: список с итогами, «Открыть» восстанавливает обе формы и робота. Кнопки **«Скачать PDF»** и **«Скачать Excel»** выгружают отчёт целиком: сценарии, состав затрат с методом и источником, исходные данные, нормативы и ограничения.

## Разработка без Docker

Нужны Node 22 и запущенный PostgreSQL (проще поднять контейнером).

```bash
docker compose up -d db
```

Бэкенд:

```bash
cd apps/api && npm ci && npx prisma migrate deploy && npx prisma db seed && npm run start:dev
```

Фронтенд:

```bash
cd apps/web/vite-project && npm ci && npm run dev
```

Адрес API для фронтенда задаётся в `apps/web/vite-project/.env` (`VITE_API_URL=http://localhost:3000`). В Docker-сборке он равен `/api` и проксируется nginx.

### Тесты экономической модели

```bash
cd apps/web/vite-project && npx vitest run
```

36 тестов воспроизводят контрольный пример из документа экономистов: количество роботов, замещение персонала, все девять статей CAPEX, OPEX, срок окупаемости, ROI, TCO и зоны интерпретации.

## Архитектура

```
robotics-platform/
├─ apps/
│  ├─ api/                    NestJS 11 + Prisma 7 + PostgreSQL
│  │  ├─ src/auth/            JWT, RBAC через таблицы Role/UserRole
│  │  ├─ src/catalog/         каталог решений: фильтры, поиск, карточка
│  │  ├─ src/projects/        сохранённые расчёты пользователя
│  │  └─ prisma/              схема, миграции, сид, данные каталога и фото
│  └─ web/vite-project/       React 19 + Vite + Tailwind
│     └─ src/
│        ├─ pages/            каталог, визард, витрина, отчёт, расчёты
│        ├─ viz/              экономическая модель + 2D-имитация склада
│        └─ store/            zustand: параметры объекта и данные экономики
├─ docs/                      статус, требования команде, аудит по ТЗ
└─ docker-compose.yml
```

**Экономическая модель** (`src/viz/economics.ts`) — чистые функции без React: пиковая потребность, количество роботов с резервом, замещение персонала через отношение производительностей, CAPEX девятью статьями, OPEX семью, RaaS, срок окупаемости, ROI, TCO, зоны интерпретации. Ни одна ставка не зашита в формулу: каждая статья — объект `{ метод расчёта, значение, источник }`, где источник помечен как «КП поставщика», «датасет» или «модельное допущение». Поэтому пользователь видит, из чего сложилась каждая цифра, и может заменить любое допущение данными коммерческого предложения.

**Имитация** (`src/viz/core/`) строит схему объекта из того же расчёта и проверяет его событийной моделью: справляется ли парк с заявленной нагрузкой. Расхождение расчёта и имитации показывается, а не скрывается.

## Источники данных

- Каталог решений и параметры объектов — датасеты организатора (`catalog_export_v4`, версия 4)
- ТТХ роботов, фотографии и цены — каталог робототехников команды (v2 от 26.09, `apps/api/prisma/data/robots-sheet-v2.csv`) по открытым источникам производителей: у каждого решения сохранены ссылка, дата актуализации и признак подтверждённости
- Стеллажные системы — лист «Стеллажи» того же каталога (`racks-sheet.csv`, 22 системы, 13 брендов): цены поставщиков, габариты секции, ярусы и нагрузка. Разбираются в `src/viz/rackCatalog.ts` скриптом `node tools/gen-rack-catalog.js`; из них берутся высота яруса для правил подбора, размер секции для схемы и цена стеллажей в CAPEX
- Экономическая модель — документ экономистов команды v2; ставки ПО, интеграции, пусконаладки, ЗИП и подготовки пола — модельные допущения
- Модуль авторизации и RBAC — собственная наработка, перенесена из личного проекта автора

## Ограничения

Результаты — **предварительная оценка, требующая верификации при обследовании объекта**. Экономическая модель не учитывает налоговые эффекты, дисконтирование, инфляцию, остаточную стоимость оборудования и лизинг; косвенные эффекты (рост пропускной способности, снижение ошибок, высвобождение площадей) не оцениваются. Подробная таблица «реализовано полностью / частично / прототип» — в [`docs/TZ_GAPS.md`](docs/TZ_GAPS.md).
