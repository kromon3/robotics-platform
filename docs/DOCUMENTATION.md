# Сопроводительная документация

Платформа подбора роботизированных решений. Хакатон «Лидеры цифровой трансформации 2026», кейс ФЦ БАС.

Документ составлен по разделам 6.1–6.10 технического задания. Инструкция по запуску — в [`README.md`](../README.md), демонстрационный сценарий — в [`DEMO.md`](DEMO.md), честная таблица «сделано / не сделано» — в [`TZ_GAPS.md`](TZ_GAPS.md).

## 1. Целевая аудитория, обслуживаемые сценарии и границы решения (6.1)

### Кому

| Аудитория | Задача | Что получает |
|---|---|---|
| Собственник или руководитель склада, производства | Понять, стоит ли вообще заходить в роботизацию | Срок окупаемости, ROI, TCO и три сценария за 10 минут без обследования |
| Инвестиционный или операционный аналитик | Подготовить материал к защите бюджета | Отчёт с составом затрат, методом расчёта и источником каждой цифры, выгрузка в PDF и Excel |
| Интегратор, вендор | Быстро проверить применимость своих решений к объекту заказчика | Каталог с ТТХ, правила совместимости, сравнение решений |

### Сценарий использования

1. Пользователь выбирает тип объекта и вводит его параметры (геометрия, хранение, грузы, грузопоток).
2. Платформа подбирает совместимые решения из каталога, **объясняя каждое исключение**, и ранжирует их по оценке из шести факторов.
3. Пользователь вводит данные для экономики (режим работы, персонал, инфраструктура, бюджет) и получает расчёт по трём сценариям: без роботизации, покупка, RaaS.
4. 2D-имитация работы смены проверяет расчёт: справится ли подобранный парк с заявленной нагрузкой.
5. Отчёт выгружается в PDF, Excel и отдельными диаграммами в PNG; расчёт сохраняется за пользователем вместе с версиями каталога и модели.

### Границы

Платформа даёт **экспресс-оценку до обследования объекта**, а не проект роботизации. Вне границ решения:

- проектирование планировки, расстановки оборудования и маршрутов — схема показывает типовую ячейку, тиражируемую по площади;
- выбор поставщика и коммерческие переговоры — цены берутся из открытых источников и прайсов, а не из КП под конкретный объект;
- технологическое обследование, замеры пола, аудит WMS — платформа спрашивает эти данные у пользователя, но не проверяет их;
- гарантия результата: во всех выгрузках зафиксирован дисклеймер о предварительном характере оценки.

## 2. Развёртывание и запуск (6.2)

Подробно — в [`README.md`](../README.md). Кратко:

```bash
docker compose up --build
```

Открыть http://localhost:8080. Поднимаются три контейнера: PostgreSQL 16, NestJS API, nginx со статикой фронтенда. При старте API накатывает миграции и засевает базу: роли, демо-аккаунты, каталог организатора, ТТХ роботов и фотографии. Порты меняются через `.env` (`POSTGRES_PORT`, `API_PORT`, `WEB_PORT`).

Разработка без Docker, тесты экономической модели и адреса Swagger — тоже в README.

## 3. Архитектура, компоненты, структура данных и API (6.3)

### Компоненты

```
[браузер] ── nginx :8080 ─┬─ / ......... статика React SPA
                          └─ /api/ ..... proxy -> NestJS :3000 ── Prisma ── PostgreSQL :5432
```

| Компонент | Стек | Ответственность |
|---|---|---|
| `apps/web/vite-project` | React 19, Vite 8, TypeScript, Tailwind 4, zustand, recharts, swiper | экраны, ввод параметров, экономическая модель, имитация, отчёт и выгрузки |
| `apps/api` | NestJS 11, Prisma 7 (`prisma-client` + `@prisma/adapter-pg`), JWT, Swagger | каталог, авторизация, роли, сохранённые расчёты, раздача фотографий |
| `db` | PostgreSQL 16 | каталог решений, пользователи и роли, проекты |

Экономическая модель и имитация считаются **в браузере**: расчёт мгновенный, не нагружает сервер и воспроизводим без сети. Сервер отвечает за данные и доступ.

### Структура данных

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `User`, `Role`, `UserRole` | пользователи и роли (RBAC — таблицами, не перечислением в коде) | `email`, `passwordHash`, `name` |
| `Company` | производитель или поставщик решения | `name`, `region`, `companyType` |
| `Product` | решение каталога | `name`, `type`, `status`, `subtype`, `category`, `price`, `ugt`, `marketPotential`, `specs` (JSON — ТТХ), `sourceUrl`, `sourceDate`, `verified`, `catalogVersion` |
| `Industry`, `Scenario`, `Case` | отрасли, сценарии применения, кейсы внедрения | связи многие-ко-многим через `ProductIndustry`, `ProductScenario` |
| `Project` | сохранённый расчёт пользователя | `params`, `econ`, `norms` (JSON — ввод), `productId`, `robotsCount`, `capex`, `opexPerYear`, `annualEffect`, `paybackYears`, `roiPercent`, `tco`, `catalogVersion`, `modelVersion` |

ТТХ хранятся в `Product.specs` как JSON, а не колонками: набор параметров у разных классов роботов различается, а справочник полей задан листом «Словарь полей» поставщика данных и может расширяться без миграции.

`Project` хранит и вход, и итог: итог — чтобы список расчётов открывался без пересчёта, вход и версии — чтобы расчёт воспроизводился (ТЗ 3.1.5).

### API

Все маршруты — под префиксом `/api/` через nginx. OpenAPI: http://localhost:8080/api/docs.

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /auth/register`, `POST /auth/login` | открыт | регистрация и вход, ответ — JWT |
| `GET /auth/me` | JWT | текущий пользователь и его роли |
| `GET /catalog/products` | открыт | каталог: `q`, `type`, `status`, `category`, `industry`, `scenario`, `sort`, `page`, `limit` |
| `GET /catalog/products/:id` | открыт | карточка с компанией, отраслями, сценариями и кейсами |
| `GET /catalog/products/total` | открыт | счётчик для дашборда |
| `GET /photos/:file` | открыт | фотографии решений (статика) |
| `POST /projects`, `GET /projects`, `GET /projects/:id`, `PATCH /projects/:id`, `DELETE /projects/:id` | JWT, только свои | сохранённые расчёты; чужой проект — `403` |
| `GET /users`, `POST /users`, `PATCH /users/:id`, `DELETE /users/:id` | JWT + роль ADMIN | управление пользователями |
| `GET /role`, `POST /role/assignRole`, `DELETE /role/revokeRole` | JWT + роль ADMIN | управление ролями |

Каталог и расчёт доступны без авторизации: барьер на входе убивает экспресс-оценку. Авторизация нужна, чтобы сохранять расчёты.

## 4. Алгоритм подбора и ранжирования (6.4)

### Шаг 1. Кандидаты

Из каталога берутся решения складских сценариев: «Внутрискладская логистика», «Внутрипроизводственная логистика», «Сортировка грузов». Программные продукты помечаются отдельно и в подбор не идут.

### Шаг 2. Жёсткие правила совместимости

Все правила собраны в одном месте (`src/viz/core/rules.js`, `src/viz/liftRules.ts`) и применяются к паре «робот ↔ объект»:

| Правило | Источник данных | Пример объяснения |
|---|---|---|
| Тип стеллажа ↔ класс робота | матрица `RACK_ROBOTS` | «FMR не работает со стеллажом „Мезонин“» |
| Тип стеллажа ↔ тип груза | матрица `RACK_CARGO` | «Фронтально-полочный стеллаж не работает с длинномерным грузом» |
| Тип груза ↔ класс робота | `CARGO_ROBOTS` | «AMR не работает с длинномерным грузом (нужны CTU/FMR)» |
| Масса груза ≤ грузоподъёмности | `specs.payload_kg` | «Груз 1200 кг тяжелее грузоподъёмности AMR (1000 кг)» |
| Ширина прохода | габариты робота и груза | «Нужен проход не уже 2,6 м, у вас 2 м» |
| Высота подъёма ≥ верхнего яруса | `specs.lift_height_mm` + каталог стеллажей | «Поднимает груз на 2,0 м, верхний ярус — 4,0 м (Экомет СПФ 27113-60-3000, 3 яруса)» |
| Масса груза ≤ грузоподъёмности на высоте | `specs.lift_residual_payload_kg` | «На максимальной высоте поднимает 800 кг, ваш груз 1200 кг» |

Минимальная ширина прохода: для роботов без вил — ширина корпуса + 0,4 м; для вилочных (FMR, CTU) — длина робота + длина груза + 0,3 м, для длинномера берётся половина длины (разворачивается боком).

Правила высоты **не применяются**, если производитель значения не заявил, а также к стационарным системам и к подпаллетным AMR — они возят стеллаж целиком, а не ставят груз на ярус. Молчаливых допущений в исключениях нет: если данных нет, правило не срабатывает.

Не прошедшие правила решения **не скрываются**: они показываются в блоке «Исключены» с перечнем причин (ТЗ 3.4.2).

### Шаг 3. Ранжирование

Прошедшие решения получают оценку 0–100 (`src/viz/ranking.ts`):

| Фактор | Вес | Как считается |
|---|---|---|
| Стоимость парка | 35 | отношение к лучшему в наборе: вдвое дороже — половина баллов |
| Число роботов | 15 | так же; меньше единиц — меньше зарядных мест и точек отказа |
| Запас грузоподъёмности | 15 | двукратный запас над массой груза — полный балл |
| Готовность решения | 15 | статус из каталога (60%) и УГТ (40%) |
| Достоверность ТТХ | 10 | паспорт / оценка по открытым источникам / типовые значения + подтверждение производителем |
| Запас по проходу | 10 | комфортным считается запас 30% ширины прохода; работа впритык штрафуется |

Оценка сравнивает решения **внутри набора подходящих** — это «лучшее из того, что подошло», а не абсолютная шкала. У каждой карточки раскрывается раскладка: сколько баллов дал фактор и из какого значения это следует. Веса заданы явно и показываются пользователю.

Сравнение до трёх решений — таблица на 21 строку: ТТХ, источник данных, требуемое число роботов и стоимость парка для введённой нагрузки.

## 5. Экономическая модель (6.5)

Реализация — `src/viz/economics.ts`, чистые функции без React. Источник формул — документ экономистов команды «Экономическая модель хакатон 2026 v2»; контрольный пример из документа воспроизводится тестами до рубля (`economics.test.ts`, 36 тестов).

### Основные формулы

| Показатель | Формула | Единицы |
|---|---|---|
| Пиковая потребность | `(приёмка + отгрузка) / (смен × часов) × пиковый коэффициент` | операций/ч |
| Эффективная производительность робота | `паспортная × коэффициент использования` | операций/ч |
| Количество роботов | `⌈пиковая потребность / эффективная × (1 + резерв мощности)⌉` | шт |
| Замещение персонала | `роботов × (эффективная производительность / выработка оператора)`, не больше фактической численности | чел. |
| Годовой эффект | `замещённые × зарплата × 12 × начисления − OPEX` | ₽/год |
| Срок окупаемости | `CAPEX / годовой эффект` | лет |
| ROI за горизонт | `(годовой эффект × лет − CAPEX) / CAPEX` | % |
| TCO | `CAPEX + OPEX × лет` | ₽ |

### Состав затрат

**CAPEX (10 статей):** роботы, зарядные станции, ПО, интеграция, пусконаладка, обучение, подготовка пола, **стеллажное оборудование**, ЗИП, резерв проекта.

**OPEX (7 статей):** сервис, лицензии, электроэнергия, связь, расходные материалы, ремонт, персонал эксплуатации.

**RaaS:** разовый платёж по договору и ежемесячный тариф за робота.

### Источники и допущения

Ни одна ставка не зашита в формулу. Каждая статья — объект `{ значение, метод расчёта, источник }`, где источник помечен одним из трёх:

| Метка | Что значит | Примеры |
|---|---|---|
| КП поставщика | цена из прайса или коммерческого предложения | роботы, зарядные станции, стеллажное оборудование (со ссылкой на прайс поставщика) |
| Датасет | взято из данных организатора или нормативных значений | начисления на ФОТ 30,2% |
| Модельное допущение | согласованная с экономистами оценка, заменяется данными КП | ПО 10%, интеграция 10%, пусконаладка 7,5%, ЗИП 2%, подготовка пола 2 500 ₽/м², резерв 10% |

Эта пометка видна пользователю в отчёте у каждой строки и выгружается в Excel — понятно, какие цифры твёрдые, а какие требуют уточнения.

### Интерпретация и чувствительность

Зоны (ТЗ 3.5.8): срок окупаемости — зелёная ≤ 2,5 года, жёлтая 2,5–4, красная > 4; ROI — зелёная ≥ 50%, жёлтая 0–50%, красная < 0; CAPEX к бюджету — зелёная ≤ 100% бюджета, жёлтая до 120%, красная выше.

Анализ чувствительности показывает, как срок окупаемости реагирует на ±20% по пяти параметрам (цена робота, производительность, коэффициент использования, стоимость труда, сервис и ремонт), отсортированным по влиянию.

### Заключение по сценариям

Под таблицей сравнения платформа формулирует вывод (ТЗ 3.7.1): какой сценарий выгоднее и почему. Решающий критерий — TCO на горизонте расчёта: он учитывает и разовые, и ежегодные затраты. Вывод сопровождается основаниями (разница TCO, экономия против сценария без роботизации, срок возврата разовых затрат) и оговорками — превышение бюджета, продолжение платежей после горизонта при RaaS, неучтённые эффекты. Если ни один сценарий с роботами не дешевле, чем ничего не делать, платформа прямо пишет, что роботизация на этих параметрах не окупается.

### Пересчёт «что если»

На экране отчёта три ползунка: зарплата оператора, коэффициент загрузки робота и цена решения. Все показатели, состав затрат, графики и заключение пересчитываются мгновенно теми же формулами. Изменённые параметры выводятся отдельной строкой, которая попадает и в печатную версию, чтобы выгруженный отчёт нельзя было спутать с исходным расчётом. Выгрузки в PDF и Excel собираются по тем значениям, что видит пользователь: в книге появляется строка «Параметры изменены вручную». На сохранённый расчёт ползунки не влияют — он хранит введённые данные.

### Чего модель не учитывает

Налоговые эффекты, дисконтирование, инфляция, остаточная стоимость оборудования, лизинг. Косвенные эффекты (рост пропускной способности, снижение ошибок, высвобождение площадей) не оцениваются — в отчёте это заявлено явно.

## 6. Загрузка и актуализация данных (6.6)

### Источники

| Данные | Файл | Происхождение |
|---|---|---|
| Каталог решений | `apps/api/prisma/data/catalog_export_v4.json` | датасет организатора, версия 4 |
| ТТХ роботов | `apps/api/prisma/data/robots-sheet.csv` → `robot-specs.json` | каталог робототехников команды по открытым источникам производителей |
| Фотографии | `apps/api/prisma/data/photos/` | там же |
| Стеллажные системы | `apps/api/prisma/data/racks-sheet.csv` → `src/viz/rackCatalog.ts` | прайсы поставщиков, ссылка у каждой позиции |
| Нормативы экономики | `src/viz/economics.ts` (`DEFAULT_NORMS`) | документ экономистов команды v2 |

### Процедура

1. **Каталог организатора** засевается `prisma/seed-catalog.ts`: денормализованные строки разбираются в компании, продукты, отрасли, сценарии и кейсы; вставка идемпотентна (`createMany({ skipDuplicates })`), повторный запуск не плодит дубли.
2. **ТТХ** засеваются `prisma/seed-specs.ts`: карточки сопоставляются с продуктами каталога **по названию** с нормализацией кириллических омоглифов («АК-2000» и «AK-2000» — одно и то же) и уточнением по грузоподъёмности; чего в каталоге нет — заводится новым продуктом и привязывается к складским сценариям.
3. **Обновление каталога ТТХ** от поставщика данных — `node prisma/tools/merge-sheet.js --write`: сопоставление идёт по названию, а не по `id` карточки, потому что при обновлении листа карточки перенумеровываются, а фотографии в проекте лежат под нашими идентификаторами. Совпавшим обновляются ТТХ, цена, источник и дата; новые добавляются; записи, которых в новом листе нет, сохраняются.
4. **Стеллажи** разбираются генератором `node tools/gen-rack-catalog.js`: цены приводятся к ₽ за место хранения (прямая цена за паллетоместо либо цена секции, делённая на вместимость), позиции «по проекту» удельной цены не получают и в выбор не попадают.
5. **Версии.** У каждого продукта хранится `catalogVersion`, у расчёта — `catalogVersion` и `modelVersion`. Расчёт, сохранённый на версии 4 каталога и модели v2, остаётся объяснимым после обновления данных.

У каждого решения сохраняются `sourceUrl`, `sourceDate` и `verified` — источник, дата актуализации и признак подтверждения производителем (ТЗ 3.3.4). В карточке и в сравнении это видно пользователю.

## 7. Руководство пользователя и администратора (6.7)

### Пользователь

| Экран | Что делает |
|---|---|
| **Dashboard** | сводка: число решений в каталоге |
| **Роботы** | каталог: поиск, фильтры по типу, категории и статусу, сортировка, пагинация; карточка с ТТХ, кейсами, источником и датой актуализации |
| **Проекты** | выбор типа объекта → визард параметров (6 шагов) → витрина подбора → данные для экономики (5 шагов) → результат |
| **Витрина подбора** | подходящие решения с оценкой и раскладкой, исключённые с причинами, сравнение до трёх решений |
| **Результат** | вкладка «Экономический отчёт» с заключением и ползунками «что если» и вкладка «Схема и имитация»; кнопки «Скачать PDF», «Скачать Excel», выгрузка диаграмм в PNG, «Сохранить расчёт» |
| **Расчёты** | сохранённые расчёты с итогами и версиями; «Открыть» восстанавливает обе формы и выбранного робота; удаление |

Ввод защищён от ошибок: у каждого поля единица измерения и допустимый диапазон, при выходе за границы поле подсвечивается, а отправка формы сообщает, что именно исправить. Кнопка «Заполнить примером» на обоих экранах ввода подставляет демо-склад.

### Администратор

Роль `ADMIN` выдаётся записью в `UserRole`. В REST API её проверяют `JwtAuthGuard` и `AdminGuard`: администратору доступны эндпоинты управления пользователями и ролями (`/users`, `/role`).

**Административный интерфейс каталога — http://localhost:8080/admin.** Вход по тем же учётным данным, что и в приложении; пускают только пользователя с ролью `ADMIN`, остальным вход отклоняется с записью в журнал.

| Раздел админки | Что можно |
|---|---|
| Каталог: решения | Создавать, править и удалять решения: название, тип, статус, категория, цена, УГТ, компания, источник и дата актуализации, признак подтверждённости, версия каталога. ТТХ правятся редактором «ключ — значение» поверх JSON |
| Каталог: компании, отрасли, сценарии, кейсы | Полное управление справочниками |
| Связи | Привязка решений к отраслям и сценариям |
| Расчёты | Только просмотр: сохранённые расчёты принадлежат пользователям и правятся в приложении |
| Пользователи и роли | Просмотр и правка профиля, выдача и отзыв ролей. Хеш пароля не показывается и вырезается из ответов API; смена пароля — только через приложение |

Технически админка построена на AdminJS с SQL-адаптером: он читает схему напрямую из PostgreSQL, поэтому не зависит от версии Prisma и подхватывает новые таблицы после миграций. Роутер монтируется в то же приложение Nest со своей сессией; если база недоступна, админка отвечает понятным сообщением и не мешает работе REST API, а следующий запрос пробует подключиться снова.

Массовое наполнение каталога по-прежнему выполняется процедурой загрузки данных (раздел 6) — админка предназначена для точечных правок и ведения справочников.

## 9. Известные ограничения и план развития (6.9)

### Ограничения

| Ограничение | Следствие |
|---|---|
| Производительность роботов в каталоге ТТХ не заявлена ни одним производителем | количество роботов считается по типовым значениям классов из документа экономистов — это главное допущение модели, оно объявлено в отчёте |
| Процентные ставки CAPEX (ПО, интеграция, ПНР, ЗИП, пол) — модельные допущения | точность оценки ±30%; заменяются данными КП без изменения кода |
| Схема — типовая ячейка, тиражируемая по площади | это не проект планировки; расстановка реального объекта отличается |
| Объекты больше 200 × 120 м и парки больше 24 роботов | схема рисует репрезентативный фрагмент, экономика считается на весь объект |
| Аэропорт и медучреждение | доступны на уровне выбора типа объекта и описания; экраны параметров в работе |
| Администрирование нормативов экономической модели | нормативы задаются в коде и вводом пользователя; отдельного справочника в админке нет |
| Интеграции с WMS/ERP/1С | описаны, не реализованы (см. ниже) |

### Возможные интеграции (ТЗ 3.8.3)

| Система | Что даёт | Как подключается |
|---|---|---|
| WMS | фактический грузопоток, структура заказов, сезонность вместо ручного ввода | выгрузка операций за период → импорт параметров объекта |
| ERP / 1С | фактический ФОТ, численность и ставки, бюджет проекта | справочники сотрудников и статей затрат → нормативы расчёта |
| Системы мониторинга оборудования | фактическая производительность и простои внедрённых роботов | телеметрия → уточнение типовых значений производительности |
| Каталоги вендоров | актуальные цены и ТТХ | периодическая выгрузка в формате листа «Каталог» → процедура из раздела 6 |

Точка подключения готова: загрузка данных отделена от приложения и идёт через CSV/JSON с идемпотентными сидами, так что интеграция сводится к подготовке выгрузки в согласованном формате.

### План развития

1. Экраны параметров и правила подбора для аэропорта и медучреждения.
2. Справочник нормативов экономической модели в админке — сейчас через неё ведутся каталог, компании, отрасли, сценарии, кейсы, связи, пользователи и роли.
3. Импорт параметров объекта из Excel по шаблону и программный интерфейс импорта каталога.
4. Уточнение производительности решений: запрос паспортных значений у производителей, накопление фактических данных с внедрений.
5. Дисконтирование, налоговые эффекты и лизинг в экономической модели; учёт косвенных эффектов.
6. Сравнение сохранённых расчётов между собой и история пересчётов объекта.

## 10. Воспроизведение демонстрационного расчёта (6.10)

Сторонний специалист воспроизводит результат так:

1. `docker compose up --build`, открыть http://localhost:8080 — данные засеются автоматически.
2. Пройти [демонстрационный сценарий](DEMO.md) — 10 шагов с ожидаемым результатом на каждом.
3. Сверить выгрузку с приложенным образцом отчёта [`sample-report.xls`](sample-report.xls): демо-склад 40 × 24 м, решение Ronavi H1500, стеллажи ДВК СТЛ Э — 6 роботов, CAPEX 34 901 900 ₽, OPEX 7 820 640 ₽/год, срок окупаемости 4,47 года.
4. Проверить экономическую модель на контрольном примере документа экономистов: `cd apps/web/vite-project && npx vitest run` — 67 тестов, из них 36 воспроизводят контрольный расчёт до рубля.

Все входные данные расчёта, нормативы и версии каталога и модели сохраняются вместе с проектом, поэтому любой сохранённый расчёт открывается и пересчитывается в том же виде.
